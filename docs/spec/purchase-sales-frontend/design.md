# 仕入・売上管理フロントエンド 設計

## アーキテクチャ

Flutter アプリを feature-first で整理し、API 呼び出しは `lib/config` と `lib/features/*/data` で管理する。

## 画面構成

- Home: 初期画面。主要機能への入口として 3 つのボタンを縦配置
- MasterMaintenance: マスタメンテナンスのサブメニュー画面
- Items: 品目マスタ。一覧・追加・変更・削除を行う。追加・変更画面では税区分（標準／軽減／非課税）を選択する
- Suppliers: 仕入先マスタ。一覧・追加・変更・削除を行う
- Menus: メニューマスタ。一覧・追加・変更・削除を行う。追加・変更画面では税区分（標準／軽減／非課税）を選択する
- TaxRates: 消費税率マスタ。一覧・追加・変更・削除を行う（税区分・税率・適用開始日・適用終了日）
- Purchases: 仕入伝票。一覧・追加・変更・削除を行う。一覧は直近7日分をデフォルト表示し、カレンダーで期間を変更できる。明細行の税率は品目の税区分と仕入日から自動セットする
- Sales: 売上伝票。一覧・追加・変更・削除を行う。一覧は直近7日分をデフォルト表示し、カレンダーで期間を変更できる。値引き額（`discount_amount`）の入力欄、支払方法の固定リスト選択を持つ。明細行の税率はメニューの税区分と営業日から自動セットする

## 画面遷移

- 起動直後の Home 画面では、上から順に「仕入伝票」「売上伝票」「マスタメンテナンス」の 3 つを表示する
- 「マスタメンテナンス」押下時に MasterMaintenance 画面へ遷移する
- MasterMaintenance 画面では、上から順に「品目」「仕入先」「メニュー」「消費税率」の 4 つを表示する
- 各ボタン押下時に、対象 domain の一覧画面へ遷移する
- 一覧画面から、追加・変更・削除の操作を行うための画面遷移を用意する
- API の GET/POST/PUT/DELETE を適切に使い分けて、WebAPI の機能をフル活用する
- 戻るボタンは AppBar の leading もしくは左上固定ボタンとして配置し、前の画面へ戻る

## API 連携方針

- ベース URL は `API_BASE_URL` で注入する
- `package:http` を利用して REST API を呼び出す
- 例: `GET /items`, `POST /purchases`, `GET /sales?from=...&to=...`, `GET /tax-rates?tax_category=STANDARD`, `PUT /tax-rates/{taxCategory}/{validFrom}`
- レスポンスのエラー時（HTTPステータスが200番台以外）は `ApiException` を投げ、画面側でハンドリングする

## APIレスポンスのパースエラー処理

- バックエンドAPIは必須項目のチェックを行わないため（「クライアント側バリデーション方針」参照）、過去に別スキーマ・別経路（Postman等）で登録された不整合なデータ（例: 消費税対応前に登録され `tax_rate` を持たない仕入/売上明細）が既存データとして存在しうる
- レスポンスJSONをモデルへ変換する処理（各 `*Api` クラスの `fromJson` 呼び出し）は、フィールド欠落・型不一致による例外（`TypeError`等）を捕捉し、`ApiException`（「データの形式が想定と異なるため読み込めませんでした。既存データが現在の仕様と一致していない可能性があります」等）に変換したうえで再送出する。生のDart例外メッセージをそのまま画面に表示しない
- 一覧画面・登録編集フォーム画面のいずれも、APIエラー時は共通の `ErrorView`（メッセージ＋再試行ボタン）を表示する。フォーム画面（品目/仕入先/メニュー/消費税率/仕入伝票/売上伝票の追加・変更画面）でも一覧画面と同様に再試行ボタンを表示する

## 仕入伝票・売上伝票の登録・編集フロー

- API側にヘッダ単独・明細単独で登録するエンドポイントは存在しない（`POST /purchases`・`POST /sales`は常にヘッダ+明細をまとめて1リクエストで送信し、Lambda側は`TransactWriteItems`でアトミックに登録する）。そのため、登録・編集画面はヘッダ入力欄と明細リストを1画面にまとめた構成とする
- 一覧画面の「追加」ボタン押下で、仕入伝票（売上伝票）の登録フォーム画面へ遷移する
- フォーム画面の構成
  - ヘッダ入力欄: 仕入伝票は仕入先（ドロップダウン）・仕入日（日付選択）・納品日（任意）・備考。売上伝票は営業日・売上日時・卓番・人数・支払方法（固定リスト）・値引き額・備考
  - 明細リスト: フォーム内に明細行のリストと「明細行を追加」ボタンを配置する
  - 集計表示: 小計・税額・合計金額を明細の入力内容から自動計算して表示する（編集不可）
  - 「登録」ボタン: 画面下部に配置する
- 「明細行を追加」ボタン押下時の挙動
  - 画面のローカル状態（未送信）に空の明細行を1件追加する。この時点ではAPIへの送信は行わない
  - 追加された行には、品目/メニュー選択（`is_active=true`のみ）・数量・単価（税抜）の入力欄と、金額（`quantity × unit_price`で自動計算・読取専用）・税率（品目/メニューの`tax_category`と伝票基準日から自動セット・読取専用）を表示する
  - 各行には削除ボタンを設け、押下でその行をローカル状態から削除する
- 「登録」ボタン押下時の挙動
  1. クライアント側バリデーションを実行する（ヘッダの必須項目、明細が1件以上あること、各明細の品目・数量・単価が入力されていること、全明細の税率が解決済みであること）
  2. バリデーションを通過した明細から `subtotal`/`tax_amount`/`total_amount` を計算する（「消費税額（tax_amount）の計算方法」参照）
  3. ヘッダフィールドと明細配列をまとめて `POST /purchases`（または `POST /sales`）に1回のリクエストとして送信する
  4. 成功したら一覧画面に戻る。失敗した場合はエラーメッセージを表示し、入力内容は保持する
- 編集（変更）画面も同じ1画面構成とする。画面表示時に対象伝票を `GET /purchases/{id}`（または `/sales/{id}`）で取得し、ヘッダ・明細をフォームに反映する。「更新」ボタン押下時は同様にバリデーション・再計算のうえ `PUT /purchases/{id}`（または `/sales/{id}`）を呼び出す（明細は全洗い替えのため、画面上の明細リストの内容がそのまま新しい明細として送信される）

## 消費税率の自動セット

- 品目・メニューの登録・変更フォームには `tax_category`（`STANDARD`/`REDUCED`/`EXEMPT`）を選択するドロップダウンを設ける（3択、必須）
- `m_item.standard_price` / `m_menu.standard_price` および明細の `unit_price` は**税抜金額**として保持・入力する（飲食店の売上には持ち帰り（軽減税率）とイートイン（標準税率）が混在しうるため、税込前提の単一価格にできない）
- 仕入伝票・売上伝票の明細行では、品目/メニューを選択した時点で以下の手順により `tax_rate` を自動セットする（ユーザーは編集不可の読み取り専用表示とする）
  1. 選択された品目/メニューの `tax_category` を取得する
  2. `GET /tax-rates?tax_category=<tax_category>` で該当区分の税率一覧を取得する（`EXEMPT` の場合も同様にAPIから取得する。クライアント側で `tax_rate = 0` を独自設定することはしない。`m_tax_rate` に `EXEMPT` 区分のレコードを都度登録・維持する運用とする）
  3. 伝票の基準日（仕入伝票: `purchase_date`、売上伝票: `business_date`）以前の `valid_from` を持つレコードのうち、`valid_from` が最も新しいものを有効な税率として採用する（バックエンドの`Query`（SK降順・Limit=1）と同じ選定ロジックをクライアント側で再現する）
  4. 該当するレコードが無い場合は、明細行にエラーを表示し登録・更新操作を無効化する
- 伝票の基準日（仕入日／営業日）を変更した場合、既に追加済みの明細行についても税率を再解決し、`tax_rate` を再セットする
- 税率一覧はマスタ画面の遷移時、または伝票入力画面表示時にキャッシュ取得し、明細行ごとの都度リクエストは行わない（同一税区分・同一基準日であれば再利用する）
- 品目・メニューの `tax_category` を登録後に変更しても、既存の伝票明細には一切影響しない。明細の `tax_rate` は登録時点の値をスナップショットとして保持しており、`item_id`/`menu_id` 経由で品目・メニューの現在の `tax_category` を参照し直すことはない

## 消費税額（tax_amount）の計算方法

インボイス制度（適格請求書等保存方式）上、1つの伝票につき税率ごとに1回だけ端数処理を行う必要があるため、以下の順序で計算する。

1. 明細ごとに `amount`（税抜合計 = `quantity × unit_price`）と `tax_rate` から `amount × tax_rate` を**端数処理せず**算出する
2. 同一 `tax_rate` の明細をグルーピングし、上記の値をグループごとに合計する（端数処理はまだ行わない）
3. グループごとの合計に対して、ここで初めて端数処理を行う。端数処理の方法は「切り捨て」とする（実務上の多数派に合わせる）
4. 各グループの端数処理後の値を合計したものをヘッダの `tax_amount` とする
5. `subtotal` は明細の `amount` の単純合計、`total_amount` は `subtotal + tax_amount - discount_amount`（売上のみ discount_amount を考慮）とする

明細単位で `amount × tax_rate` を都度端数処理してから合計する実装は行わない（複数明細で誤差が蓄積し、インボイス制度の要件にも反するため）。

## 一覧画面の日付範囲UI

- 仕入伝票・売上伝票の一覧画面を開いた時点で、`from`＝7日前、`to`＝当日として `GET /purchases`・`GET /sales` を呼び出し、直近7日分を初期表示する
- 期間はカレンダー形式の日付範囲選択UI（Flutterの`showDateRangePicker`等）で変更できるようにする。期間変更後は選択された `from`/`to` で再取得する

## 支払方法（payment_method）

- `payment_method` はAPI上は自由文字列だが、フロント側では固定リスト（現金／クレジット／電子マネー）から選択するドロップダウンとし、選択した文字列をそのまま送信する（自由入力欄は設けない）

## 値引き額（discount_amount）

- 売上伝票フォームに `discount_amount` の数値入力欄を設ける（未入力時は0として送信する）
- `total_amount = subtotal + tax_amount - discount_amount` として自動計算する（「消費税額（tax_amount）の計算方法」参照）

## 論理削除済み品目・メニューの扱い

- 仕入伝票・売上伝票で新規に明細行を追加する際、品目/メニューの選択肢は `is_active=true` のもののみとする
- 既存の伝票を編集する場合、その明細が参照している品目/メニューが論理削除済み（`is_active=false`）であっても、選択済みの項目として表示を維持する。名称には「(取扱終了)」等のラベルを付与し、他の非active品目/メニューは選択肢に含めない
- 一覧・詳細（閲覧専用）画面では、`item_id`/`menu_id` から品目/メニュー名を解決して表示する。論理削除済みでも通常通り表示する（是正削除ではないため名前解決自体は常に可能）

## クライアント側バリデーション方針

- バックエンドAPI（Lambda）は必須項目のチェックを行わず、不正・不足したリクエストもそのまま登録してしまう（openapi.yamlの`required`はドキュメント上の取り決めに過ぎない）。そのため、送信前のクライアント側バリデーションを必須とする
- 品目登録: `item_name`, `unit`, `tax_category` が未入力の場合は送信をブロックする
- メニュー登録: `menu_name`, `category`, `standard_price`, `tax_category` が未入力の場合は送信をブロックする
- 仕入伝票: `supplier_id`, `purchase_date`, `details`（1件以上）が未入力の場合は送信をブロックする
- 売上伝票: `sales_datetime`, `business_date`, `payment_method`, `details`（1件以上）が未入力の場合は送信をブロックする
- 消費税率マスタ登録: `tax_category`, `description`, `rate`, `valid_from` が未入力の場合は送信をブロックする

## 環境変数

```bash
flutter run --dart-define=API_BASE_URL=https://<api-id>.execute-api.<region>.amazonaws.com/stg
```

- API のベース URL は `--dart-define=API_BASE_URL=...` を優先する
- `--dart-define` を指定しない場合（`flutter run -d chrome`等でのローカル開発時）は、`.env` の `API_BASE_URL` にフォールバックする（`flutter_dotenv` を使用。`.env` が存在しない場合は読み込みをスキップし、次のフォールバックに進む）
- どちらも無い場合は `http://localhost:8080` をデフォルト値とする
- 優先順位: `--dart-define` > `.env` > デフォルト値

## 状態管理

- 初期実装では `setState` ベース
- 画面遷移状態は `Navigator.push/pop` で管理する

## レイアウト配慮

- 画面幅が狭い場合でもボタンが押しやすいよう、余白を確保し、縦並びのままスクロールできるようにする
- ボタン高さは十分に確保し、タップしやすいサイズにする
- 一覧表示は必要に応じて `SingleChildScrollView` や `ListView` でスクロール可能にする
